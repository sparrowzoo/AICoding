# 接口设计与声明

<a id="api-first"></a>
从一个具体调用出发，说明谁在什么场景调用、提供方接受什么、调用方如何判断结果。交付项目中可以定位、审阅和验证的接口定义。已满足本轮需求的接口直接复用，给出源码位置和适用理由。

独立审查直接读取现有声明和调用方，返回审查意见。单独委托写接口时，按[执行方式](../develop-work-flow/references/authorization.md#execution-choice)和[本轮授权](../develop-work-flow/references/authorization.md#stage-authorization)核对目标、允许改动的文件及适用的[分支约定](../develop-work-flow/references/authorization.md#requirement-branch)。TRD 已获准的接口任务沿用同一范围，两种入口都可以直接使用本 skill。

## 确定接口范围

1. 从已确认的业务场景或技术目标找到真实调用方、提供方和模块边界。查阅双方当前源码、既有协议、版本与用户最新修改。新增入口时说明哪个调用需求无法由现有接口满足；改动公共签名时列出受影响的调用方、旧消息或已发布客户端。
2. 在项目使用的定义中写清方法或事件、身份与权限来源、输入、成功结果、失败结果及可观察的副作用。字段给出业务含义、类型、可空与缺省值；标识来源、单位、分页次序、幂等或重试等只写与本次调用相关的约定。异步接口分别说明收到请求、处理完成和处理失败如何被观察。
3. 对照一个成功场景和适用的失败或历史数据场景，核对调用方能否构造请求、区分结果，旧调用方能否继续工作。公共行为发生变化时，说明兼容办法、受影响方和待决定事项。业务规则有分歧交给 PRD，跨模块职责、存储方案或实施顺序需调整时交给 TRD。

通过用户级软链接调用时，从本文件的真实位置解析相对引用。读取[接口、数据结构与框架约定](references/engineering-contracts.md)。写 Java 声明时读取 [Java 协议分包](references/java-protocol-layout.md)，采用 CODER 的[对象命名](../coder/references/java-object-naming.md)和[类型引用](../coder/references/java-type-imports.md)规则。Sparrow HTTP 项目可对照[返回协议示例](references/response-example.md)核对已有类型。

<a id="layer-contracts"></a>
## Controller、Repository、DAO 接口与 PO 字段怎么定义

沿本次场景的实际调用顺序，找到涉及的层。已有声明能满足要求时，给出文件、类型和具体方法或字段；新增或变更时，交付下列定义。

| 对象 | 需要交付的定义 |
| --- | --- |
| Controller（HTTP 入口） | 列出 HTTP 方法和路径、处理方法签名，以及路径、查询、请求头和请求体各自绑定到哪个参数或协议字段。说明调用哪个用例、身份从哪里取得、成功响应和失败状态如何返回。分别写清方法返回类型和客户端实际收到的响应。 |
| Repository（面向业务的读写接口） | 从用例调用方出发，定义每个业务方法的签名、业务入参、返回类型，以及未找到、冲突或存储失败时调用方会得到什么。采用 Sparrow 分层时，接口归 domain，infrastructure 中的实现负责调用 DAO 和转换数据；业务签名使用领域类型或稳定协议类型。 |
| DAO（数据访问接口） | 从 Repository 实现实际需要的读写动作出发，给出 DAO 方法签名。查询指明存储查询类型、筛选条件、排序、分页和空结果；写入指明接收的 PO 或更新参数、匹配条件，以及返回主键或受影响行数的含义。已有基类方法可用时，引用具体方法和它在本实体上对应的类型。 |
| PO（持久化对象） | 交付 DAO 实际读写的类型声明，标明对应表、主键及其生成方式。字段逐项对应对象属性和表列，注明语言类型、存储类型、可空性、默认值，继承字段引用基类。指出哪些字段要转换为业务对象或 DTO，谁负责转换，特别说明名称、类型或单位的差异。 |

TRD 确定读写行为、数据归属和表列映射。api-first 据此交付各层签名及配套类型声明，由 TRD 引用同一份源码或拟议差异。单独受托设计接口时，以现有结构和已确认的约束为依据；需要改变存储设计时，将具体差异交回 [TRD 的数据结构设计](../trd-writer/SKILL.md#data-structure-design)。Java 项目的基类、对象转换与字段映射按[持久化约定](../coder/references/java-persistence.md)核对。执行数据库变更仍需单独授权。

## 写出并审查真实接口

先定位项目实际使用的定义，如 HTTP 路由、RPC 接口定义文件、事件消息格式或跨模块方法签名。采用生成代码的项目从权威定义入手。用户仅委托文稿时，在文稿中说明拟议的定义与尚缺的源码。只读审查直接报告源码位置、调用场景、问题和建议。

一组交付覆盖[本次涉及的层](#layer-contracts)、API 方法签名及其实际使用的协议类型。采用 Java 协议分包时，写入参数定位到 `protocol.param` 的 Param，读取条件定位到 `protocol.query` 的 Query，结构化结果定位到 `protocol.dto` 的 DTO。每个入参、返回值都能追到具体类型，每个新增或变化的协议字段都能查到名称、类型、含义、是否必填、是否允许空值及适用的校验。复用现有类型时引用实际定义，无参方法、简单返回值或其他语言的接口沿用项目原有表达方式。

- **能与现有调用方、实现以及已发布数据兼容的声明**，在允许写源码的范围内直接落到目标文件，保留既有方法体和业务行为。必要时核对类型、序列化样例或已有调用的编译结果。新增 Spring MVC 方法需要方法体时使用明确的未实现占位。
- **会使现有调用或实现失效、破坏旧消息或客户端兼容性的声明**，在设计阶段先保留项目中可用的版本。基于真实文件交付可审阅的源码差异，标明目标路径、基线版本（含未提交内容的可复核依据）、受影响的提供方与调用方，以及需要一起迁移的部分。在现有授权内检查拟议声明能否应用到该基线、类型或协议是否成立，如实记录已检范围、结果和仍需实施后验证的事项。把实际差异或其可复核位置随方案交给用户，避免只交方法名或伪代码。
- **应用不兼容改动**时，先核对本版定义、基线和用户明确批准的实施批次。编码者在该批次一起迁移受影响的声明、实现和调用方，再核对旧引用、相关模块编译和协议验证。基线或方案已产生影响兼容性的变化时，先报告差异和影响，请用户确认受影响部分。已发布客户端或历史消息无法同批更新时，报告影响，采用用户已确认的兼容或迁移安排。
- **交付结果**指明复用的定义、已写入的声明或待应用的差异，分别说明声明检查与实际业务验证。属于 TRD 的任务用稳定接口编号关联场景、源码版本或差异基线，供方案和计划引用。

## 谁安排接口声明，谁接收结果

api-first 根据已确认的业务场景和技术约束定义接口，对语义和交付负责。每组声明只指定一方编写。无论由负责接口设计的代理亲自编写，还是委派给其他代理，实际编写声明源码或拟议源码差异前，都必须先使用 [coder 的声明模式](../coder/SKILL.md#interface-code)并遵守其规范。单独委托接口时，api-first 核对结果后向用户交付。接口属于 [TRD](../trd-writer/SKILL.md) 时，api-first 核对声明或差异，TRD 将结果纳入本版方案报用户审阅。委派沿用原授权，遇到需要改变已定语义的问题，先报告具体差异及其影响。

例如，订单列表新增“按状态筛选”。Controller 说明 `GET /orders` 的 `status` 如何绑定到 `OrderQuery.status`，省略时沿用旧查询。Repository 声明接收业务查询、返回分页订单 DTO 的方法。沿其实现找到 DAO 的分页方法，说明业务状态如何转成存储查询条件。再从 PO 定位实际的状态列，核对读出的值如何转成 DTO 的状态字段。交付时把示例名称换为项目里的真实签名和字段，SQL 实现及联调由后续获准的编码批次完成。
