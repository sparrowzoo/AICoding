文档首先遵守[清楚、适量、复用原则](../develop-work-flow/SKILL.md#documentation-principle)：仅展开本次需求及变化，未变内容引用既有章节；full/lite 不决定篇幅，模板不要求机械填满。

共享执行规则来自 [develop-work-flow](../develop-work-flow/SKILL.md)。通过软链接加载时，先解析本文件的真实路径，仅用于定位技能包内的 skill、agents、脚本和模板；执行时不回源仓库读取设计文档。目标业务项目的需求、产品、技术、代码与证据仍是必要任务输入，应按本次范围读取。首次写入前执行主工作流的[需求分支准备](../develop-work-flow/SKILL.md#requirement-branch)，续做或阶段交接时核对并复用对应分支；只读审查不切换工作区。

# 技术设计与计划

先按[新需求独立成文](../develop-work-flow/SKILL.md#requirement-document-boundary)确定文档归属：每次新需求在独立需求目录重新编写当前阶段文档，重复内容用适用说明与具体章节链接复用。下文沿用目录、保留编号、原位更新与跨轮承接仅限同一需求的修订和继续执行，不适用于后续新需求；不能因为属于同一产品或修改存量功能而并入旧文档。

交付遵守[产物内容边界](../develop-work-flow/SKILL.md#artifact-relevance)：skill 规则变更对业务文档透明，直接维护当前有效内容；不在正文、评审区或业务 evidence 中记录规则调整、旧文档问题及重构过程。真实业务变化、授权与验证记录仍须保留。

文档中的人员、团队与职责按[相关人确认](../develop-work-flow/SKILL.md#stakeholder-confirmation)核实；缺少必要信息时集中询问用户，不用“未指定”或其他占位词替代确认，已确认的角色／团队及后置安排按实际范围复用。

先读取[公共工作流](../develop-work-flow/SKILL.md)和 [DSL 规范](../develop-work-flow/SKILL.md#dsl)，按[阶段授权](../develop-work-flow/SKILL.md#stage-authorization)核对上游结论、当前产物与进入技术设计的授权；直接调用本 skill 也遵守相同门禁。输入为目标项目 `doc/<需求目录>/` 中按 mode 维护的需求、产品规则、验收场景及当前授权；在已授权设计范围内补齐必需输入，不把设计授权当作实施授权。

按[分流规则](../develop-work-flow/SKILL.md#routing)维护 `technical.md` 与 `plan.yaml`，生成 `plan.md` 与 `task-status.md`，两者均为首次计划交付的必备产物。编写前按[需求性质确认](../develop-work-flow/SKILL.md#requirement-kind)核对用户标识；未明确时先提示确认，不先写文档。明确技术需求可省略 BRD/PRD，不引入业务方或产品经理；技术复杂度及方案评估仍须明确。需求性质（技术／业务产品）、复杂度（简单／复杂）和文档布局（lite／full）分别记录。简单业务需求可采用 lite 并省略 BRD/PRD，复杂业务需求采用 full；lite/full 不表示复杂度。技术需求省略产品文件时使用工具的 lite 文档布局，不等于复杂度简单。`mode: lite` 时 TRD 同时承载目标、规则、正文 R 锚点及有行为任务的唯一 Gherkin 代码块（`acceptance` 锚点；纯文档等无行为任务按 DSL 例外处理）；不要求 req/prd/独立场景文件。`mode: full` 时读取需求和产品文档，场景正文在 acceptance.feature。两种模式均保留任务追溯、真实测试及四列验收状态。

两种模式编制前读取 [TRD 模板](../develop-work-flow/assets/feature/technical.md)，按[主工作流模板规则](../develop-work-flow/SKILL.md#trd-template)核对本次适用内容；可合并、简写或省略无关章节，公共规范引用既有来源，不机械保留九章及全部表格。稳定编号、接口、测试、验收和授权锚点放在相应语义章节，元信息按事实填写。

## 本轮模式与跨轮承接

遵循[迭代承接](../develop-work-flow/SKILL.md#iteration)：mode 沿用现有文档来源契约，不因小迭代自动切换，同一需求保留目录与 R/S/T 编号，新编号递增。TRD 头部标明从需求目录派生的稳定编号 `TRD-<需求目录>` 并使用 `trd` 锚点。历史引用注明迭代及可核实的 Git 基线；未提交来源按公共规则保留必要摘录与版本状态，不伪造提交或自指当前文件。

- 同一需求的纯技术小迭代：只更新原 TRD 的相关设计，不新开目录、不重写 BRD/PRD；计划、状态和证据按实际影响同步，未变内容引用。
- 同一需求的产品逻辑小变更：同步更新原 PRD 的受影响规则，并按影响更新场景、TRD 与计划。不得用 TRD 的变化覆盖未同步的 PRD。原需求按规则没有 PRD 且仍符合省略条件时，在原 TRD 维护规则与场景。
- 业务需求由简单扩为复杂，或确认采用完整业务文档集：原小 TRD 的稳定编号与可复核版本来源先在 REQ/evidence.md 留证，由需求阶段整理业务输入，再按阶段完成 PRD。技术阶段接收已交付 PRD，并承接原技术基线；不要求 PRD 引用 TRD，覆盖同一路径后历史引用不能自指当前文件。
- 新迭代保留未完成任务的原 ID，以及计划仍需要的 done 前置任务及其传递依赖闭包。撤出任务须有用户确认、原因和 evidence；只保留本轮与必要基线，基线任务备注非本轮新增成果，引用与证据须仍匹配当前代码。

## 设计深度

按[需求评审边界](../develop-work-flow/SKILL.md#requirement-review-boundary)承接上游已确认的业务原则、验收结果和留待本阶段完善的技术事项；在当前授权范围内形成具体方案，不要求用户返回需求阶段逐项批准纯技术机制。发现方案改变业务效果、范围、数据归属或成本承诺时，先呈交受影响的业务取舍，不擅自改写已确认需求。

展开详细设计前执行[重大设计边界确认](../develop-work-flow/SKILL.md#design-boundary)：先核实需求来源、已有系统和数据归属，呈交必要的简明提案并确认重大取舍，再细化相关表、接口和任务。进入 TRD 环节或存在旧草稿不代表其中的扩张设计已获认可。

所有技术产出及附录遵守公共工作流的[人类可读强制规范](../develop-work-flow/SKILL.md#human-readable)。先解释业务用途与设计理由，再写真实接口、表和字段；数据字典使用“字段名、中文含义、完整类型、可空、默认值、说明”的逐字段表格，通用字段列实际全名并引用完整定义。禁止私有类型、空值、作用域或审计组合编码，即使附有图例也不使用。

`technical.md` 按内容组织模块职责、依赖、数据与关键流程；接口章节形成足以直接实施的公共和跨模块契约，建立 `api-01` 等显式稳定 anchor，说明签名、字段类型与校验、输出、错误、副作用及关键实现步骤；数据章节维护本次所需的逐字段存储设计。不要另起概要／详细设计的平行结构。

设计先核对现有代码和外部接口事实；未知信息明确标注，不把推测写成已经具备的服务。仅在存在有意义取舍时比较方案，不强制两个选项、固定篇幅、每个私有函数签名或与实现同等冗长的伪代码。完整模式引用按[指定 PRD 模板](../develop-work-flow/SKILL.md#prd-template)编写的 product.md，承接其中的目标、规则、指标、灰度与相关数据等产品规格，仅补充技术实现、接口、物理结构、验证和发布恢复设计，不另定义或复制业务正文；不要求 PRD 为未变背景重复展开。轻量模式在 TRD 维护规则，按实际改动组织内容。高风险简单需求仍可轻量，但必须说明风险、影响角色和范围、控制措施；文档精简不豁免阶段授权，通知按公共规则执行。

按[环境授权](../develop-work-flow/SKILL.md#environment-authorization)在 TRD 成组列出需要评估的环境动作、对象、影响、资源或费用、隔离及恢复与验证方式，供用户与具体方案一并确认。范围内的环境授权可以复用，超出范围重新确认；环境获批不等于业务阶段获批，不因准备测试环境提前实施未授权动作。

## 测试设计

在 TRD 的 test-strategy 锚点下按 [RIGHT-BICEP](../develop-work-flow/SKILL.md#right-bicep) 逐维考虑正确结果、边界、反向关系、独立交叉验证、错误条件与性能。写明适用场景/测试引用或不适用理由；轻量模式可紧凑说明并合并不适用项，无需六行表；需要性能验收时给出有依据的负载、环境和阈值/基线。技术与测试引用统一使用该需求目录（如 req-r01-profile）。

## 确认与任务

新旧功能均按[阶段授权](../develop-work-flow/SKILL.md#stage-authorization)交付可审阅的具体 TRD 与计划，在实施前取得用户对该方案及实施范围的明确授权。按[接入约定](../develop-work-flow/SKILL.md#onboarding)核对用户级 grilling，对需要用户判断的决定通过 grill-me 或 grilling 分组分轮确认，随回答完善草案；不能把澄清答案自动解释为最终实施授权。涉及历史功能逻辑变更时，无论 `lite` 或 `full`、风险高低，还须按[存量确认](../develop-work-flow/SKILL.md#existing-confirmation)说明历史文件、函数/接口、当前行为、本次改动与保留行为、受影响调用方、新接口契约和关键代码设计，以及回归与必要发布恢复措施。明确每个相关模块、类/函数的职责、调用关系和允许修改的边界。记录用户结论、批准对象与范围及未决项；新旧由当前代码分析确定，一般实施授权、文档完整或“内部调整”不能替代所需的具体方案确认。

复杂新功能和复杂存量变更均须经过具体 TRD 与计划的用户评审，不能沿用“新功能直接实施”例外。自主执行例外仅按公共规则判断并留证；纯文档也遵守对应阶段门禁。已明确批准的同一对象和范围不重复确认；发现新的历史逻辑影响或超出已确认范围的设计时，先补齐可审阅方案，再确认受影响部分，不重走整条流程。按既定可独立交付边界划分阶段，不把每次工具调用当作阶段，也不临时合并阶段规避授权。

按可验证的功能小步拆分任务，遵循跨轮依赖保留规则，在 `plan.yaml` 中维护稳定 Task ID、需求/场景/设计引用、项目相对文件路径、依赖和验证命令；字段、状态、备注和证据格式以 DSL 规范为唯一来源；remark 用于最终四列任务状态列表的简短说明。验证命令应运行真实测试，并使 Gherkin 场景可追溯到测试实现与结果。合理的 TDD 例外要说明原因与替代验证，不能用环境故障伪造 RED。

TRD 确需排期时使用简表，任务用 T 编号链接 DSL 或生成的阅读计划，不重复任务正文、依赖和状态；开发者、日期、人天仅在该表维护，按确认填写，未知标待确认，不擅自扩展 DSL 字段。

并行规划按[归并规则](../develop-work-flow/SKILL.md#collaboration)由一名协调记录者写 plan/evidence 和生成视图，其他执行者回传结果。由记录者依次运行公共工具 `workflow.mjs validate`、`render`、`status`、`check`，核对生成视图与来源一致。首次规划交付即生成状态表，后续持续刷新；交付前确认 TRD、任务计划源、阅读计划与状态列表均存在；不可手改 `plan.md` 或 `task-status.md` 的生成正文；末尾独立评审区按评审状态规则维护。工具位置、依赖准备及参数见 [工作流脚本入口](../develop-work-flow/SKILL.md#script-entry)。

复杂或高风险设计按公共规范安排本阶段必要的独立审查；没有相应工具时如实自审，不伪称独立通过。交付前对照 TRD 模板核对本次内容充分性、适用约束和锚点引用，并检查正文、附录和生成阅读视图的人类可读性，先修正再交付；DSL 校验成功不能替代这些检查。交付实际项目根、feature、TRD 与 DSL 及阅读计划、关键结论、取舍、风险、未决项、结构与可读性检查结果和授权状态。报告后按阶段门禁等待用户明确批准当前具体方案与实施范围，再交给 coder；文档生成、校验通过或内部审查均不能替代用户授权。本 skill 只产出设计计划，不自动实施、提交、推送或部署。

按[全链路证据](../develop-work-flow/SKILL.md#evidence)记录到同目录 `evidence.md`，并行时交由协调记录者归并：记录上下文、实际需求/代码/确认输入、技术与计划输出、校验结果和证据位置。lite 将需求与产品记录合并于技术阶段，仍链接 TRD 内对应事实；仅规划时将实施、测试和验收标为未执行。

所有本次交付文档最末按[文档评审状态](../develop-work-flow/SKILL.md#document-review-status)维护“评审结论”，记录实际审查、用户确认及下一环节授权；取得答复或发生影响结论的修改后同步更新，不能沿用失效批准。生成视图只维护独立评审区，机器可读文件用末尾注释，不改变任务或场景契约。
