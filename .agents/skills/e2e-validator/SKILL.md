# 功能验收

先读取[公共工作流](../../../design-docs/workflow.md)和 [DSL 规范](<../../../design-docs/AI Coding 设计说明.md#dsl>)。输入为目标项目 `doc/<需求目录>/` 下按 mode 维护的权威规则、场景、TRD、任务 DSL、`evidence.md` 及实际实现和测试结果：lite 的规则与 Gherkin 场景在 technical.md，full 使用产品和独立场景文件；不要求 lite 补齐完整文档集。沿用 `R01`、`S01`、`T01` 等现有标识，不重新编号或另造一套场景。

1. 检查本迭代每个已承诺场景与真实测试实现、执行命令和结果的关联。Gherkin 场景内容存在、测试代码存在或命令退出成功但没有执行目标场景，都不足以证明验收通过。
2. 按 [RIGHT-BICEP](../../../design-docs/workflow.md#right-bicep) 核对适用维度的用例与证据，检查反向/交叉验证是否独立有效、错误是否实际触发、性能是否按约定条件测量；不适用理由合理且未跳过已承诺目标。运行公共 `validate`/`check`，并核实任务证据对应当前实现。自动结果只能证明它实际覆盖的行为；按风险执行必要的集成或端到端验证，不机械要求每条规则凑齐固定类别。
3. 对失败给出规则/场景、触发条件、实际结果和证据位置；对环境限制、未执行项和不确定结论明确标注。已有有效测试结果可复用；发生相关修改、失败或覆盖疑点时才补充执行。
4. 核对任务完成状态、实际改动的历史文件/函数/接口、改变与保留行为和用户细节确认范围一致；验证原有调用方及约定回归用例，实际实现须符合已确认的模块/函数职责与设计边界，新旧判断需有代码分析依据。高风险改动的风险、影响角色和措施应在文档中可见，不要求外部通知。未经确认的行为改变不能以测试通过代替授权；发现问题交回对应任务，修复后复验受影响部分。

验收直接引用 DSL 证据及自动测试结果，规则、场景和追溯信息各自保留唯一来源。两种模式均按[全链路证据](../../../design-docs/workflow.md#evidence)核对并汇总同目录 `evidence.md`：每个实际环节必须有上下文、输入、输出、结果及可定位来源。检查调查/确认、需求产品（lite 合并于 TRD）、技术计划、实施测试、审查、验收与提交交付的证据是否连贯，是否对应当前版本；缺失、未执行或未验证明确列出并说明下一步，不能宣布该部分通过。人工验收和审查记录写入 evidence.md，DSL 保留任务证据摘要，长日志引用真实报告，不重复维护业务规则或任务状态。状态或证据变化后通过公共工具重新生成 `plan.md`。

## 最后验收交付

先根据验收结果更新 plan.yaml 的 status、remark 和 evidence。失败、受阻或待验证事项在 remark 简述原因与下一步；未执行或未通过不能标为 done。随后按[工作流脚本入口](../develop-work-flow/SKILL.md#script-entry)依次执行 render、status、check（--project 指向项目根，--feature 填完整需求目录，如 req-r01-profile）。

必须在该需求的 `doc/req-【需求】/` 下生成独立 `task-status.md`，只显示“任务编号、名称、状态、备注”四列，列出本轮所有任务；即使未全部通过也如实交付。状态表由 DSL 生成，不手改，不增加标题、统计或证据列。详细规则见 [任务状态列表](../../../design-docs/workflow.md#task-status)。

交付 `evidence.md` 的全链路核对结论和未决项，并记录本次实际验收输入、输出及执行结果；工具校验不会代替这项核对。

按公共规范决定是否值得独立审查，披露实际审查方式。最终区分通过、失败和未验证项；无发现就说明无发现，不能将未验证写成通过。本 skill 不自动修业务代码、推送或部署。
