# 框架复用、重试与状态管理

当获批任务涉及以下行为时，定位实际入口、负责执行的组件和生效配置，按本次场景核对。下文的重试、快照和异步流程是对应场景的实现与检查示例。设计没有约定这类行为时，遵循 [CODER 的实施范围](../SKILL.md#implementation-scope)。调用方能观察到的结果以 [api-first 的接口定义](../../api-first/SKILL.md)和获批方案为准。

## 复用已有执行逻辑

沿现有调用链查明谁负责调度、重试、次数限制和异常处理。对照项目锁定版本的源码、配置和对应版本的官方示例，再决定需要补哪段代码。框架能力未经核实时，记录待验证的方法和受影响的行为。

已有消息发布器和处理器时，将新业务接入已有分发点。使用 Spring AI 实现 ReAct 工具循环时，先核对谁驱动循环、谁限制调用次数、工具异常会走哪条分支。只在当前组件缺少已确认的行为时补实现；重复注册处理器、再套一层循环或重试，都可能让同一操作执行多次。

## 失败重试与持久化

沿一次请求列出会改变状态的动作，核实部分成功后是从哪一步恢复、依据哪份已保存的结果判断前一步已完成。同一业务事实只生成和保存一次；有不同含义的记录，按各自的事务和交付时点处理。涉及 Java 持久化时，按[持久化规则](java-persistence.md)检查实际查询、保存和返回值。

例如，模型结果已持久化、下游推送失败时，用已保存的结果重试推送。覆盖该失败分支，核对模型执行、结果入库和推送各自的次数及最终内容。若约定支持并发重试，还要核对两个执行者同时恢复时会留下几条结果。

## 连接、身份与异步任务

会话通过 HTTP 接口打开、切换或恢复时，每次操作都按当前可信身份与目标做授权检查。连接目录只管理连接实例和生命周期。设备键可以复用时，关闭回调删除映射前须核对实例，避免旧连接晚到的回调移除已建立的新连接。覆盖新旧连接按这个顺序交错的场景。

请求线程从项目已有入口取得可信身份，向异步工作显式传递本次所需的数据。处理器接受的动作以该方向已定义且已授权的事件为准，公共枚举里存在同名值本身不能开放业务入口。采用 Sparrow 时核对[身份来源与 HTTP 接入](../../api-first/references/engineering-contracts.md#sparrow-controller)。

## 配置快照与历史重现

按代码配置生成快照的项目，用选择键定位配置，用固定版本记录当次采用的内容。内容相同时复用已有快照，变化时建立新快照并保留旧版本。若业务要求重现一次执行，记录当时服务端按策略选定的版本及历史范围；实现和读取时区分单条历史明细与整次执行上下文。查询时分别使用设计指定的业务主键和局部顺序号，例如按 `messageId` 找消息、用 `seqNo` 定位会话内顺序。

## 核对变更后的调用链

从用户最近确认的源码和协议出发，逐项同步受影响的调用方、映射、注解和测试，保留已确认的分包与删除。按本次改动分别报告声明或序列化、独立样本、真实查询与持久化、推送或端到端用例的结果。若只有编译通过，应说明尚未运行的业务路径。审查输出沿用 [CODER 的代码审查要求](../SKILL.md#code-review)。
