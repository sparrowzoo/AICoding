文档处理统一遵循[清楚、适量、复用](../develop-work-flow/SKILL.md#documentation-principle)、[模板结构](../develop-work-flow/SKILL.md#template-structure)及[最新结论与同步](../develop-work-flow/SKILL.md#decision-sync)；自查和评审按[全链路逻辑审查](../develop-work-flow/SKILL.md#logic-review)执行当前阶段适用项。本 skill 只维护本阶段特有要求，不复制共用规则正文。

共享执行规则来自 [develop-work-flow](../develop-work-flow/SKILL.md)。通过软链接加载时，先解析本文件的真实路径，仅用于定位技能包内的 skill、agents、脚本和模板；执行时不回源仓库读取设计文档。目标业务项目的需求、产品、技术、代码与证据仍是必要任务输入，应按本次范围读取。首次写入前执行主工作流的[需求分支准备](../develop-work-flow/SKILL.md#requirement-branch)，续做或阶段交接时核对并复用对应分支；只读审查不切换工作区。

所有代码及设计中的名称遵守[直接、简单、明确、见字识意的统一命名规范](../develop-work-flow/SKILL.md#readable-naming)，覆盖API、类、接口、对象、方法和数据库表字段，不限于文档标题。

类、方法、参数和变量按长期稳定的业务职责命名，读名字就能知道用途，不用 `Mvp`、`V1`、`V2` 等阶段或版本标签给会持续迭代的业务类命名。例如通用会话接入类不命名为 `MvpSessionController`，避免下次迭代批量改名。新增业务代码以可读性为先，尽量使用 Java 8 之前的直白语法；避免为简短而使用 lambda、Stream、`var`、record、模式匹配或新式 switch 等语法糖。确有必要时写清楚意图；不为语法风格单独重写无关存量代码。

## API FIRST：先完成整个调用链的协议

- 编码前先读取本需求已确认的 TRD、接口契约、传输协议和任务依赖。这里的“协议”包括 HTTP/WebSocket 的外层字段和载荷、前后端参数与返回对象、业务接口的方法及出入参、模型与业务上下文对象、Repository 接口，以及 DAO 接口及其查询条件、PO 等出入参。上下文对象也属于协议，不能等业务逻辑写完再临时补类型；具体类仍按已确认模块职责放置，不因称为协议就把 PO 或数据库类型塞进公共 protocol 模块。
- 先列清每个受影响接口的提供方和调用方、方法签名、对象字段、类型、可空性、取值和时间单位、身份来源、错误、排序与幂等含义；按已确认命名创建可编译的 Param、Query、DTO、上下文及持久化接口类型。跨端二进制协议还须明确每个字节、长度、分支、编码方向与边界，不以只解析其中一段代替完整帧解析。先用独立样本检查前后端字段与字节一致，再实施 Controller、业务服务、编解码器、DAO 实现和页面。
- 任务计划若已把契约与实现分开，按依赖顺序完成契约任务的类型、签名和验证，再开始实现任务。没有单独契约任务时，也在当前已授权实现范围内先完成这一步；计划或契约缺失、互相矛盾时先修正可审阅的契约与受影响任务，不能从实现草稿自行反推并冻结公共接口。已确认契约无需重复请用户决定；真正未定的业务字段或外部接口再集中说明影响并询问。
- 实施中需要改变已定义的字段、上下文对象或 DAO 出入参时，先同步权威契约、所有受影响的接口签名和前后端样本，再改调用方与实现；不得只改某一层、在 Controller 中临时拼散参数，或让 DAO 返回值与上层对象靠猜测转换。接口契约验证通过只说明输入输出一致，不能代替业务行为和数据库验证。

## 执行链与优先返回

- 沿一次请求或任务的完整执行链检查重复工作：同一身份读取、校验、查询、转换或外部调用由明确的一层执行一次，后续层传递并使用结果，不在 Controller、服务和适配器中无意义地重做。确因并发状态变化、事务边界或安全要求需要再次校验时，说明两次检查各自的时点和目的；外部副作用还须保持幂等。
- 接口采用优先返回：先检查必要前提，不成立时立即抛出约定的业务异常或返回已定义的结果；正常路径保持直线，避免深层嵌套。不要在已可确定结果后继续查询或调用外部服务，也不要为了早返回跳过必需的提交、清理或授权检查。
- 测试除返回值外，还核对关键依赖的调用次数和副作用；无效请求应在发生不必要的查询、模型调用或写入前结束。

## 优先使用框架已有能力

使用任何框架实现功能前，先核对项目实际使用的版本，再查该版本的官方文档、官方示例和公开配置参数，优先按官方支持的方式接入。示例与本项目版本不一致时先核实差异，不能直接照搬；现有框架已提供的执行、限制、重试和异常处理能力不另造一套。确实缺少所需能力时，先说明已查到的官方入口、缺口和拟补的最小适配范围；找不到相关官方示例或无法确认正确用法时，向用户询问，不凭猜测实现。

Spring AI 的 ReAct/工具调用尤其先核对并使用官方现有的工具循环、最大调用次数及异常处理策略和参数，不自行编写并行的 ReAct 循环或替代性异常策略。只在官方能力无法满足已确认业务规则时，设计必要的业务边界适配，并说明原因及验证依据。

## Sparrow 认证与 HTTP Controller 边界

编写或修改本项目业务接口前，读取当前需求已确认的 HTTP 契约及项目已有的 `ControllerAdvice`。代码或计划与用户确认的契约不一致时，先按最新确认的契约修正；仍有冲突则先交付受影响接口的具体差异，不自行发明参数或认证流程。

- 认证由已引入的第三方 Passport/认证组件及过滤器负责。业务用例可直接读取 `SessionContext.getLoginUser()` 和 `SessionContext.getClientInfo()`，后者返回 `ClientInformation`；不为同步调用链另建 `TrustedUserContext` 等等价包装。不要再在 Controller 中调用 `authenticate(instance, sessionId, token)`，不要解析 token、请求头或客户端信息，也不自建认证、登录态或请求头认证协议。若 `ClientInformation` 缺少业务需要的信息，先询问用户，不自行扩展或补解析。业务归属和操作权限仍按已确认业务规则，基于可信身份校验。跨异步边界时在请求线程取得所需可信信息并显式传递，不在异步线程重新读取请求线程的 `SessionContext`。
- HTTP 契约命名先核对已确认的权威定义：写入参用 `Param`，读取参用 `Query`，返回业务数据用 `DTO`；前端字段名、JSON 字段、Java 对象及领域调用保持同一含义，不另造等价 `Request`/`Response` 名称。约定为请求体的接口直接以 `@RequestBody` 接收参数对象，不先收 `String body` 再手工解析。路径中已有的业务标识可在 Controller 与请求体组装成完整业务参数对象，再传给服务；不重复传认证头或客户端信息，也不接受彼此冲突的重复标识。不要随意增加 `@PathVariable`、`@RequestHeader`、`HttpServletRequest` 或零散标量参数。
- 修改接口出入参时同批更新实际调用它的前端、服务签名和契约测试，验证字段名、请求绑定、返回数据与统一响应一致；不要只改 Java 端而让页面继续发送旧字段或旧凭据。
- Controller 只做格式、必填与对象组装；业务约束由对应业务服务保证。已有层完成的校验结果沿调用链传递，不为分层形式在下一层机械重复同一检查。
- 参数、字段和方法名见字识义，不另造别名、猜测字段或在 Controller 中重复解析请求。
- Controller 只返回具体业务 DTO 或业务结果。统一响应外壳和异常映射由已有 `ControllerAdvice` 处理；Controller 不返回 `ResponseEntity<Result<T>>`，不手工创建 `Result<T>`。
- 可预知的业务不成立条件优先使用 `com.sparrow.exception.Asserts.isTrue(condition, errorSupport)` 抛出 `BusinessException`；核对条件方向：该方法在 `condition` 为 `true` 时抛异常。不要为返回错误手写 `if/else`、`switch`、HTTP 状态码或错误响应对象；正常业务分支仍按业务需要表达。业务错误枚举实现 `com.sparrow.protocol.ErrorSupport` 的现有方法；核对项目实际的 category/模块编码规则，末尾两位错误码按自然顺序排列，不给接口臆加字段或方法，也不用 HTTP 状态码充当业务码。由 `ControllerAdvice` 统一转换异常响应。
- 修改 Controller 时检查方法签名、认证来源和返回类型，并以相关测试核对实际请求绑定及统一响应。不得为了让旧测试通过而恢复散参数、手工 token 处理或 Controller 内的响应包装。

## 代码 review：检查完整调用链

代码自审或用户要求的代码 review，先按公共工作流的[审查集中反馈](../develop-work-flow/SKILL.md#review-feedback)确定本轮范围、依据和报告方式。只读 review 不触发实施；获准编码批次内的自审与修正属于该批次，不冒称独立端到端验收。审查实际 diff、调用方、被调用方、配置与相关测试，不只看改过的单个方法或任务勾选状态。

- **契约与同步：** 从最新确认的业务规则和协议出发，核对前端提交与渲染、Controller 绑定、`Param`／`Query`／`DTO`、完整二进制帧、领域用例、上下文对象、异步消息、Repository与DAO接口及其出入参、PO映射、持久化字段和对外事件中的名称、含义、类型、可空性及生成方；检查旧字段、旧凭据和旧消息路径是否仍被调用。修改一处契约时同步修正本批次全部受影响的代码、测试与必要文档，不留前后端各说各话。
- **执行顺序与副作用：** 顺着正常、失败、重复、并发、重试、强制控制及恢复等适用路径，逐步核对认证来源、优先返回、单链路去重、领号／入队／确认／落盘／推送等实际先后关系；检查幂等键、唯一约束、事务边界、失败后是否丢失或重复副作用，以及只由指定节点执行的动作。不适用的路径说明原因，不为假设中的极端情况新增未经确认的机制。
- **项目边界与框架：** 核对模块依赖、接口归属、运行时装配、配置、迁移和版本兼容是否与本次改动匹配；优先查当前版本的官方示例与参数，复用框架能力。检查可信 `SessionContext`、统一响应／异常、`Asserts` 与 `ErrorSupport`、业务可读命名和直接易读的语法；仅在相关调用链内处理这些问题，不借 review 扩大重构范围。
- **验证与结论：** 检查测试能否观察关键状态和副作用，尤其是调用次数、顺序、唯一性及错误分支；记录实际执行的命令、结果、代码版本与环境，区分单测、构建、启动和业务验收。用户已给出的运行结果按对应版本承接；相关代码改变后补做必要验证，不把未执行写成通过，也不因旧环境失败否定新的结果。汇总全部发现后按触发条件、位置、影响、证据和修复方式定级；在已授权范围内先修正并复验，剩余问题一次性报告。无发现仅表示本轮已检查范围内无发现。

# 按计划实施

按[新需求独立成文](../develop-work-flow/SKILL.md#requirement-document-boundary)读取本次需求自己的文档与计划；跨需求仅按章节引用读取所需基线，不合并旧需求文档、任务或证据。下述编号延续和跨轮承接仅限同一需求。

先读取[公共工作流](../develop-work-flow/SKILL.md)和 [DSL 规范](../develop-work-flow/SKILL.md#dsl)，再读目标项目的 `doc/<需求目录>/plan.yaml`。DSL 是任务、状态和证据的权威来源，`plan.md` 只供阅读，禁止手工维护。按本轮 mode 与[迭代承接](../develop-work-flow/SKILL.md#iteration)读取权威来源：lite 读取 TRD，存在历史基线时一并读取其引用的原需求/文档，已有 PRD 的产品规则以同步后的 PRD 为准，TRD 不得覆盖与其冲突的规则；发现冲突先回到设计环节澄清；full 读取产品、场景及设计文件。按任务引用读取技术契约，不把规划目录当作源码根，也不为 lite 补建完整文档集。

## 开始条件

先按[阶段授权](../develop-work-flow/SKILL.md#stage-authorization)核对具体 TRD、计划与本实施批次的用户授权，直接调用本 skill 也遵守相同门禁。读取分流依据和影响说明，不凭需求名称决定是否询问；复杂新旧功能均须先交付具体方案并获批准，文档完整、内部审查或泛泛的“开始开发”不替代所需授权。自主执行例外仅按公共规则判断并留证，不以新功能、纯文档、基础代码或并行任务绕过。涉及历史功能逻辑变更时，无论 `lite` 或 `full`、风险高低，还须按[存量确认](../develop-work-flow/SKILL.md#existing-confirmation)核对代码位置、模块/函数职责、调用边界、接口与关键实现、改变与保留行为及回归范围。缺少确认时报告缺口，按已授权的调查设计范围补齐可审阅方案，再通过 grill-me 或 grilling 取得必要决定；不能先修改受影响逻辑。已明确批准的同一对象和范围不重复确认，超出范围的新设计再确认。仅获工作流或文档修改授权时，不自动实施其中的业务案例。

本实施批次按既定可独立交付边界确定，包含对应任务的 RED/GREEN、必要自审或独立检查与证据整理；不把每次工具调用当作阶段，也不临时合并批次或把独立 e2e 验收、提交纳入编码来规避门禁。开始环境动作前按[环境授权](../develop-work-flow/SKILL.md#environment-authorization)核对 TRD 中成组批准的对象与范围；范围内复用环境授权，超出范围先确认，环境获批不替代业务阶段授权。

按[工作流脚本入口](../develop-work-flow/SKILL.md#script-entry)运行 `validate`，并核对工作区现状。在已授权批次内按依赖选择任务，避免覆盖用户或其他执行者的未提交修改；串行或并行及上下文交接统一遵循[运行时分工规则](../develop-work-flow/SKILL.md#collaboration)。主代理与子代理执行同一门禁，任务独立不等于已获下一阶段授权。

跨轮任务只保留本轮与必要基线，核对未完原 ID、done 前置的传递依赖闭包及其当前有效证据；基线任务不计本轮新增成果。发现撤出无确认或依赖缺口，先交回规划修正，不自行删除依赖。

按[并行归并](../develop-work-flow/SKILL.md#collaboration)指定一名协调记录者维护 plan/evidence 和生成视图；串行由当前执行者负责。下面的状态、证据和视图更新由该记录者执行，子执行者只回传任务结果与证据。

## 小步执行

1. 将任务标记为 `doing`，确认其需求、场景及接口依据；先核对全部前置契约任务已完成，并检查相关上下文对象、业务及DAO接口的入参和出参已经定义且与前后端样本一致。按技术文档的 [RIGHT-BICEP](../develop-work-flow/SKILL.md#right-bicep) 测试设计实施适用用例，核对精确断言、独立参照和错误注入；性能验证使用已约定条件。先把对应场景绑定到真实测试；运行测试，记录确由目标行为缺失引起的 RED。
2. 实施足够满足本任务的修改，运行计划指定的验证及受影响检查，记录命令、结果和可定位证据。GREEN 必须来自真实执行，不能用静态阅读或模拟成功代替。
3. 如实维护 RED/GREEN/review 证据；非适用 TDD 的任务按公共规范记录 `tdd_exception` 及替代验证。环境阻塞与业务失败分开记录，未完成验证不能标记 `done`。
4. 按[代码 review 检查项](#code-review)通读实际调用链，按风险选择自审或独立审查；收齐发现后修复并复验受影响部分。复杂或高风险工作有可用独立执行能力时采用独立视角；没有则披露自审与限制。
5. 完成本任务所需检查后按公共规范维护状态和证据，重新生成阅读计划；同步运行 status 生成或更新必备的 task-status.md 状态列表，再运行公共 check 检查生成视图一致性。真实证据与完成条件仍按公共规范核对；测试通过不自动授权提交。

按[返工规则](../develop-work-flow/SKILL.md#rework)处理验收打回：由验收方定位，协调记录者把被打回任务及所有直接/间接依赖它的任务统一设为 blocked，备注上游打回待复验；旧结果在 evidence.md 保留并标失效，清除相关任务 DSL 中已失效的 green/review，不作为当前有效证据。返工按阶段授权确认的对象和范围实施，再按依赖顺序恢复并复验；不自动回滚代码，独立且仍在已授权批次内的工作可以继续。

同一任务连续两次失败或被打回时，按[邮件通知规则](../develop-work-flow/SKILL.md#notify)发送提醒并停下等待用户确认，其余独立任务继续。

实施中发现新的历史逻辑影响、超出已确认代码方案的新设计，或业务/范围/外部契约变化时，暂停受影响任务，按已授权范围补齐可审阅的具体方案并报告，再请用户确认；确认前不得实施变化部分，其余独立且仍在本批次授权内的工作可以继续。已确认方案和批次范围内的实施细节可自主完成，必要时同步 DSL 和技术设计；“内部实现调整”不是豁免具体设计确认的理由。不要扩大到无关重构，不自动提交、push、合并或部署。

本批次完成后报告完成与未完成 Task、代码范围、测试及审查结论、剩余阻碍与下一环节，按[阶段授权](../develop-work-flow/SKILL.md#stage-authorization)取得授权后才能进入下一批实施、独立 e2e 验收或提交；已明确批准的同一对象和范围不重复申请。获准提交时再使用 Conventional Commits 与 `Task` trailer，按公共追溯规则精确匹配完整任务值；提交、push、合并、部署分别核对对应授权。不能用「代码已写」代替「功能已验证」，也不能用验证通过代替阶段授权。

每个任务交接前按[全链路证据](../develop-work-flow/SKILL.md#evidence)向协调记录者交接结果，统一更新同目录 `evidence.md`，记录实施上下文、实际输入与代码输出、RED/GREEN 和审查结果及其证据位置，关联 T 编号。任务状态与证据摘要仍维护在 DSL，完整日志与既有提交用引用连接；不得以计划命令代替执行记录。

所有本次交付文档最末按[文档评审状态](../develop-work-flow/SKILL.md#document-review-status)维护“评审结论”，记录实际审查、用户确认及下一环节授权；取得答复或发生影响结论的修改后同步更新，不能沿用失效批准。生成视图只维护独立评审区，机器可读文件用末尾注释，不改变任务或场景契约。
