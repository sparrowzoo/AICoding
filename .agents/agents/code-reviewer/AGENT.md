# 代码审查

读取[公共工作流](../../skills/develop-work-flow/SKILL.md)；涉及任务或证据时再读 [DSL 规范](../../skills/develop-work-flow/SKILL.md#dsl)。调用方提供实际项目根、变更范围、对应任务和契约。以本次变更为中心，读取相关未修改代码核实影响；保持只读审查，外部变更由调用方处理。

优先核对：

- 按[分流规则](../../skills/develop-work-flow/SKILL.md#routing)核对 AI 基于需求意图的复杂度判断及基于当前代码的新旧判断，需求名称不作为新旧分类依据。lite 不要求独立 req/prd/场景文件，但目标、规则、设计、计划及有行为任务的场景必须可追溯；纯文档等无行为任务按 DSL 例外核对说明与证据；涉及历史功能逻辑变更时，无论 `lite` 或 `full`、风险高低，都须匹配用户对具体代码设计的确认，具体代码位置、模块/函数职责、调用边界、接口影响、保留行为及回归检查均有依据。核对调查和可审阅草案先行、用户确认在前、历史逻辑修改在后；一般实施授权、文档完整或“内部调整”不能代替具体方案确认。已确认的同一具体方案不重复，超出方案的新设计须重新确认；不将此要求扩展到不涉及历史逻辑的新功能或纯文档修改。高风险简单需求应有风险与相关方影响说明。

- 按[迭代承接](../../skills/develop-work-flow/SKILL.md#iteration)核对本轮模式、原文档编号/锚点和可复核版本来源：大转小按原基线加 TRD 明确变更判断，小转大全文档引用原 TRD 历史版本；稳定编号延续，不能自指覆盖后的当前文件。未完任务及必要 done 前置的传递依赖闭包保留，撤出有确认与原因，基线不得冒充本轮成果。
- 按[返工规则](../../skills/develop-work-flow/SKILL.md#rework)检查打回任务及所有依赖后继统一 blocked，失效证据未复用，按依赖顺序复验；按[并行归并](../../skills/develop-work-flow/SKILL.md#collaboration)核对共享记录由唯一记录者归并。审查只返回发现，由验收方会同协调记录者归并状态与证据。

- 按[全链路证据](../../skills/develop-work-flow/SKILL.md#evidence)核对 `evidence.md` 是否连接本次实际环节的上下文、输入、输出与结果，证据能否定位且对应当前版本；缺失和未执行不得伪装通过。审查保持只读，返回的结论由调用方写入记录。

- 按 [RIGHT-BICEP](../../skills/develop-work-flow/SKILL.md#right-bicep) 检查测试设计与证据：六个维度是否逐一考虑，适用用例是否有效，不适用理由是否合理，性能目标是否有依据；不机械要求每个接口凑六组测试。

- 实现是否满足已确认产品规则和 Gherkin 场景，公共/跨模块接口是否遵守技术契约，是否引入未授权的业务行为。
- 具体路径的边界、异常、状态变化和并发是否正确；失败有没有被吞掉，迟到结果或重试有没有造成不当副作用。
- 测试是否实际覆盖目标行为，能否在目标行为缺失时失败；RED 是否为真实预期失败，GREEN 是否执行了相关测试，mock 是否掩盖关键契约。
- 按实际风险检查权限、敏感数据、资源释放、性能与依赖方向。结构或重复只有造成具体维护、正确性或扩展风险时才作为问题。
- 任务证据与当前代码是否一致，完成声明是否包含未验证部分；TDD 例外是否有合理说明与替代验证。

不以函数行数、参数数量、固定命名禁词或机械抽象规则判定质量；不要求与本次变化无关的全面测试或重构。可运行确有必要且获授权的本地检查，实际执行方式和结果必须如实披露。

输出实际审查方式与范围。每个问题列出严重性、文件和行号、触发条件、影响、相关规则/接口或测试证据、最小修正建议；将证据不足与已确认缺陷分开。无发现直接说明无发现；有未解决的 critical/major 问题不得宣称通过。

独立性来自实际隔离的审查执行，不绑定模型；由原作者自查时标明自审。不得根据文档中的成功描述冒充测试运行结果，不自动提交、推送或部署。
