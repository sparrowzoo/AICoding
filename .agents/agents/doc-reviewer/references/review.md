# 审查、反馈与确认记录

<a id="logic-review"></a>
## 全链路逻辑审查

涉及技术契约、代码或调用链时，先按[SOLID与接口职责](../../../skills/api-first/references/engineering-contracts.md#solid-interface-design)完成职责和对象边界检查，再执行下列业务推演；声明/测试通过不能代替职责判断。

编写自查与正式 review 使用同一套检查方法；按本阶段职责和已确认范围判断适用项，不能只逐文件检查格式或只看改动行。先按[确认与同步](document-quality.md#decision-sync)固定最新依据，再追踪 **业务规则 → 正文与图 → 协议及接口 → 上下文与数据 → 场景及任务 → 对外结果**，覆盖引用链中的现行文档及仍被使用的旧文档。不是本阶段产物的项目不机械补建，但发现下游现有文档与当前决定冲突时应指出具体位置。

1. **先走正常业务。** 用具体输入走通首次使用、后续操作和重新进入到最终可见结果。每个必需标识/字段明确生成方、产生时点、传递来源和后续用途；下一步输入能由前一步输出或已定义来源提供。区分操作者、内容作者、接收者与业务归属，检查权限来源和对象映射，不允许先要求某 ID、后面才创建该 ID 的循环前提。
2. **分别核对各类顺序。** 涉及异步消息或任务时，分别检查业务编号/展示、入队、执行、提交、推送与确认进度；只有已确认的保证才能证明两者相同。按事件类型核对每一步的条件、责任方和持久化事实；强制操作是否取消旧任务沿用最新决定，不能从“先执行”自行推导“旧任务无效”。
3. **把状态与真实结果对应起来。** 收到、入箱、受理、处理完成、持久化成功和客户端确认分别对应什么事实；失败/重试重复哪一步、复用哪个标识、是否重复外部副作用。查询与补偿核对选取范围、排序、边界及去重关联，不能用“有序、不丢不重”代替这些定义。
4. **核对完整契约与实现计划。** 在 TRD 阶段及涉及技术契约的审查中，沿前后端、业务上下文、Repository、DAO/PO 与存储字段检查名称、含义、类型、可空性、单位及约束；二进制协议核对全帧、双向分支和独立样本。任务前置产物必须完整，逐批次推演能否编译和执行约定检查，不能只确认依赖图无环；不兼容签名与调用方迁移不能被拆成互相无法验证的批次。已明确列入前置任务的待实施工作不因尚未编码就算设计遗漏，但其职责、出入参与依赖必须明确。尚未编码的设计检查不能被写成实际构建或运行结果。
5. **再走适用分支与异常。** 检查已支持的失败、重复、并发、重试、强制及恢复路径，用具体事件验证当前约束是否已覆盖风险；已接受的边界不反复发问，也不扩大成更强保证。问题必须指出触发步骤、冲突的最新规则、实际影响及全部关联位置，不能以想象中的场景推翻当前决定。

完成后按[集中反馈与复审规则](#review-feedback)汇总、去重和核实修正；覆盖范围、不可检查部分及实际证据如实记录。关键词搜索、标题比对、链接检查只是辅助，不能代替上述业务推演。

<a id="review-feedback"></a>
## 审查问题一次性汇总反馈

**同一轮 review 先检查完约定范围，再一次性反馈全部已发现的问题；不得问一次说一次，或发现第一项就结束审查。** 本规则适用于需求、产品、TRD、计划、代码与验收的自审、独立审查，以及主代理汇总反馈。

用户要求文档 review／审查时，调用方按[文档审查并行规则](../../../skills/develop-work-flow/SKILL.md#doc-review-parallel)按本轮工作量安排 [doc-reviewer](../AGENT.md)执行只读审查，先按[确认与同步](document-quality.md#decision-sync)确定当前依据，再汇总报告。用户仅要求 review 时不改方案正文；已有修订授权时，调用方再在该范围内修正、复查。日常起草自检不因此强制调用独立审查者。

- **先固定本轮依据与检查范围。** 列出文档/代码实际版本或工作区快照、授权范围、最新确认与排除项，并标明适用检查项。并行审查者使用同一份依据，分工须覆盖跨文档关系；审查期间正文变化时只补审受影响部分，不能汇总不同版本结果后宣称当前整体通过。按[确认与同步](document-quality.md#decision-sync)区分已确认事实、旧说法和未决建议。
- **全链路逻辑审查必做。** 按[统一检查方法](#logic-review)完成当前阶段的适用项；修订按[确认与同步](document-quality.md#decision-sync)处理全部影响位置，不能以局部修改、自检或历史报告替代当前版本的整体结论。
- **检查任务能否按依赖实施。** 新计划在编号尚未固定时，按真实依赖从小到大编号；已有编号须遵守[跨轮任务承接](../../../skills/trd-writer/references/planning.md#iteration)，不能为了排版重用旧 ID。所有任务的前置条件及展示顺序必须反映实际依赖；数据契约、存储、队列、接入与验证等工作若有先后要求，计划与 TRD 使用同一顺序。核对每项任务有明确产物、边界、验证方式和适用的环境前提；不要因为文档中出现多个步骤就额外拆出无必要的任务，也不要把已确认的后续版本目标当成本轮缺口。
- **先核实风险，再定严重程度。** 对发现的问题给出最小具体场景：前提、操作顺序、在哪一步违反哪条当前约定、用户看到什么结果，并核对已有同步点、约束及版本范围。先检查正常使用与明确支持的分支，再检查相关异常；已被前置约束排除的假设不作为现行缺陷。具体故障不能被“概率低”掩盖；未经证实的极端假设也不能升格为阻塞或驱动额外机制。需要实验才能判断的事项标明验证方法和所属阶段，不让用户反复回答 AI 可以自行核实的技术问题。
- **交付前做一次完整复查。** 汇齐各章节和审查者发现，合并同类问题，处理互相冲突的建议；同一根因涉及多处时列全位置，不逐文件重复扣分。当前环节内可直接修正的遗漏先修正，并复查其全部影响点。随后检查现行正文、任务、生成视图和末尾评审状态是否指向同一版本，实际执行适用的结构检查。问题清单一次列全，分别标注已修、阻塞、非阻塞、未验证及确需用户决定的事项；新证据出现后可以再审，但上一轮漏查须明确承认并补齐。
- **用户说“review／审查／评审”时，默认交付可行性报告和打分结果，不能只回复“没问题／已通过”，也不能等用户追问才给报告或分数。** 报告按本轮实际范围，用人话讲清：能不能做、逻辑是否正确、功能与任务是否完整、全部阻塞及缺失、已接受的非阻塞TODO、验证依据和未验证范围，以及下一步建议。小范围审查可给简短报告，不机械扩展成完整研发流程；文档 review 按 [doc-reviewer 报告规则](../AGENT.md#doc-review-report)保存新轮次报告，其他已有报告按实际范围同步更新，并在回复中给出结论、分数及链接。
<a id="scoring-rubric"></a>

- **先确定审什么，再确定按什么打分。** 沿用用户已指定的评分项与权重。复审或用户缩小审查范围时，只更新被审对象和对应证据，直到用户明确调整评分口径。评审 TRD，或联审 PRD、TRD、Workflow 如何指导技术设计时，默认采用下文的[五项评分表](#trd-scoring)。审规范时用条文、模板或工具行为作依据，说明这些规则能否指导相应设计。其他文档在用户和负责规范均未指定维度时才自选。
- **交付前主审逐行对表。** 先按适用评分表列出全部行，再填写每项得分、满分、判断依据及扣分影响，并复算总分。涉及多个 skill 时，skill 名用于标注证据来源。漏项、擅自改按文件打分或分项加总有误时，先补正再交付。某项不适用时保留该行，按适用规则说明原因及分值分配。默认满分 100 分，证据不足时标明暂评分和缺失依据，阻塞问题单列。写明分数衡量的是方案准备度、实现质量还是验收情况；运行结果、用户确认及实施授权按各自证据判断。
- **不足100分必须同时交付逐项扣分与补齐清单，不让用户追问“为什么不是满分、到底还缺什么”。** 每项列明：扣几分、具体缺失或问题及其位置/依据、对当前目标有什么实际影响、是否阻塞、补齐动作、完成后如何检查，以及由AI自行处理还是确需用户决定；各项扣分之和必须等于100减总分。已在本轮修好的问题不继续计入当前扣分，只在处理记录保留。
- 扣分依据必须具体，不能只写“还有优化空间”“尚未验证”或为显得谨慎固定扣分。未验证须说明究竟哪项行为/证据未检查及如何补证；方案审查不得仅因尚未进入编码阶段而扣实现未完成的分。用户已接受的TODO、明确排除的范围和后续阶段工作不自动算当前缺失；确实影响当前评分时说明具体影响。已无当前范围内的扣分依据就如实给100分，并明确该分数只代表本轮已检查范围，不保证不存在未知问题。
- **复审要能结束。** 按原问题编号核对修正落点与关联影响，区分已修复、未修复、已接受边界和新发现；未变化且证据仍有效的部分直接承接。约定范围已检查、全部已知问题已归类、必要修正已复查、引用/生成视图与结论一致时即可交付。没有新变化、新证据或未决检查，不为凑分数重复启动整轮审查；用户明确要求再次全面 review 时仍按要求执行。新增发现说明属于方案变化、新证据还是上一轮遗漏；遗漏须承认并补查同类位置，不能归咎于用户或为维持“一次性”而隐瞒。
- 必要资料缺失导致部分检查无法完成时，一次说明缺失资料、受影响范围与当前全部已知问题，继续完成不依赖该资料的检查；不能把未检查部分说成无问题。用户明确要求分轮审查时按其安排，但每轮仍完整汇总该轮范围内的问题。

<a id="trd-scoring"></a>
## TRD 评审必须由 LLM 逐项打分

每轮 TRD 评审（含复审）都由负责审查的 LLM 阅读同一版本的方案、已确认的需求或技术目标，以及相关源码、接口和数据定义。报告必须列出以下五项。模型要根据具体场景推演设计结果，再给分；计划脚本和格式检查的结果仅作为辅助证据。

| 评分项 | LLM 据什么判断 |
| --- | --- |
| 逻辑是否自洽 | 对照已确认需求核查计划开头的理解。选一个核心场景，沿任务顺序核对前提、操作、状态变化、上下游交付和用户看到的结果。检查正文、流程图和验收场景在成功、失败及适用的重试路径上是否一致。 |
| 方案是否可行 | 对照现有代码、依赖能力、运行环境和任务顺序，判断每个关键步骤能否执行和验证。指出尚待证实的前提，以及该前提不成立会影响哪一步。 |
| 技术方案和技术选型是否合理 | 分别说明模块分工能否解决本次问题，以及所选框架、存储或中间件为什么适合当前约束。结合已有能力、维护成本和实际风险判断复用或引入技术的理由。 |
| 数据库表结构设计是否合理 | 从一次实际写入和读取核对表的用途、主外键或关联字段、字段类型与可空性、唯一约束、索引和 PO 映射。涉及存量数据时，检查兼容、迁移和恢复方案。沿用已有表也要判断它能否支持本次读写。 |
| 接口定义是否逻辑闭环 | 沿一个真实调用，检查调用方能否构造请求、提供方能否完成处理、返回值能否驱动下一步、失败能否被识别和处理。按实际涉及的 Controller、Repository、DAO、PO 和协议字段核对签名、含义及兼容性。 |

**报告按“评分项、得分／满分、判断理由与证据位置、扣分及影响”逐行填写，再给出总分和能否实施的结论。** 满分项也要给出支持判断的场景和文档章节、源码符号或其他可定位依据。阻塞问题单列，并写清修正后怎样复查。复审引用上一轮报告，说明哪些分数因哪些修正发生了变化。

默认每项 20 分，合计 100 分。某项经核实不涉及本轮范围时，保留该行，标明“不适用”和理由，将其分值均分给其余适用项，并列出调整后的满分。例如，本轮完全不读写数据库，数据库项不计分，其余四项各 25 分。需要数据库或接口设计却缺少资料时，该项仍适用，给出暂评分、缺失依据及影响。总分汇总各项实得分，存在阻塞时明确写“待修订”。

<a id="document-review-status"></a>
## 所有文档末尾明确评审结论与用户确认状态

**本工作流产出的所有正式文档均须在最下方保留独立的“评审结论”章节。** full／lite、新建／修订均适用，覆盖 PRD、TRD、独立数据设计、计划、任务状态、验收报告和 evidence 等，不因没有专用模板而省略。历史文档在本次实际触及或交付时补齐，不把未重新审查的存量文档标为通过。此章记录当前文档的真实状态，属于文档交付内容，不是 skill 维护过程；无关编写和工具日志仍按[内容边界](document-quality.md#artifact-relevance)分离。

- **写清对象与依据：** 文档／版本及评审范围、评审日期与实际审查方式、审查状态与结论、阻塞问题及非阻塞待办、未验证范围、用户确认状态、确认日期及来源、下一环节与实际授权范围。使用稳定的 `review-conclusion` 锚点，未发生或证据不足时直写“未审查”“待确认”“未验证”，不得预填通过、无问题或用户已同意。
- **分别记录两类状态：** 文档审查使用“未审查／待修订／待复审／已审查（无阻塞）”；用户确认使用“待确认／已确认／未通过／需重新确认”。审查无阻塞只代表可提交用户评估，不能自动变成用户确认或下一环节授权；“已确认”必须对应用户实际确认的对象、版本和范围，不能把某份文档的批准复制给其他文档。业务验收、运行验证和代码完成状态另按证据核对。
- **按事件更新：** 起稿设置初始状态；自审或 doc-reviewer 审查结束后，调用方／协调记录者将实际结论摘要附在本章，可附完整短结论或引用详细报告；用户答复后立即更新确认状态、依据和已获授权范围。reviewer 保持只读，不代用户确认。有未解决的 critical／major 问题写明待修订；非阻塞事项写清影响及处理阶段，不能用一句“通过”遮蔽。
- **绑定当前版本：** 业务规则、范围、契约、关键方案或证据发生影响原结论的改变时，受影响文档标“待复审／需重新确认”，保留历史结论及失效范围；无关修改不撤销其他文档的有效批准。仅补录真实评审、用户确认或修正不影响含义的排版时，说明正文未变，复用已有确认，不反复要求批准。
- **摘要与原始记录分工：** 末章是当前状态摘要，原始答复、评审发现／处理、版本快照及历史结果在 `evidence.md` 或实际审查报告留存并精确引用；二者不得维护相互矛盾的授权。evidence 自身末章只说明它已核对的记录范围，不能把其中某份文档已批准误写为整份 evidence 或全部业务已批准。记录不需要用户单独批准时明确“不适用”及依据，不据此扩大授权。
- **保持模板和机器契约：** PRD／TRD 按文档大前提适量组织，最末保留“评审结论”，可简短记录并链接证据，不复制过程日志。`plan.yaml`、`acceptance.feature` 等机器可读产物在文件末尾用原生 `#` 注释写同名章节和状态摘要／证据入口，不加入未支持的 schema 字段，也不放入会被当作任务或场景执行的正文。
- **生成视图也覆盖：** `plan.md`、`task-status.md` 的生成正文继续只读；末尾由生成器隔离的评审区允许协调记录者维护。`render/status` 在生成正文完全一致时保留末章，正文或来源摘要变化时重置当前状态为待复审／需重新确认并保留历史评审；旧格式首次补章写未审查／待确认。`check` 严格比较生成正文并校验末章边界及来源绑定，不认证评审或用户批准的真实性。评审记录归末章，任务正文沿用[状态表格式](../../../skills/trd-writer/references/planning.md#task-status)。协调记录者先生成，再仅编辑 `<!-- ai-coding-workflow:review:start -->` 与 `<!-- ai-coding-workflow:review:end -->` 之间的评审内容，保留控制标记、必需字段和对象／来源摘要。来源摘要按源文件全文计算，补录源文档状态也可能触发保守失效；核实正文含义未变后可复用有效原确认并注明依据，不机械要求用户再次批准。

交付前核对文档头部状态、末章和 evidence 一致，再按[环节授权](../../../skills/develop-work-flow/references/authorization.md#stage-authorization)报告；文档获批只在其明确范围内生效。下一环节尚未授权时明确记载，不因本章完整而自动推进。
