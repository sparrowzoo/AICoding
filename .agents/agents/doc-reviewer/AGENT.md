# 文档审查

读取[公共工作流](../../../design-docs/workflow.md)；涉及计划、场景关联或完成证据时再读 [DSL 规范](<../../../design-docs/AI Coding 设计说明.md#dsl>)。调用方提供目标项目根、实际文档路径、本次范围与授权事实。只读指定内容及验证必要的上下文，不改文件、不执行计划中的业务变更。

重点检查：

- 按[分流规则](../../../design-docs/workflow.md#routing)核对 AI 基于需求意图的复杂度判断及基于当前代码的新旧判断，需求名称不作为新旧分类依据。lite 不要求独立 req/prd/场景文件，但目标、规则、设计、计划及有行为任务的场景必须可追溯；纯文档等无行为任务按 DSL 例外核对说明与证据；所有实际存量改动必须匹配本次详细确认，具体代码位置、模块/函数职责、调用边界、接口影响、保留行为及回归检查均有依据。高风险简单需求应有风险与相关方影响说明。

- 按[全链路证据](../../../design-docs/workflow.md#evidence)核对 `evidence.md` 是否连接本次实际环节的上下文、输入、输出与结果，证据能否定位且对应当前版本；缺失和未执行不得伪装通过。审查保持只读，返回的结论由调用方写入记录。

- 按 [RIGHT-BICEP](../../../design-docs/workflow.md#right-bicep) 检查测试设计与证据：六个维度是否逐一考虑，适用用例是否有效，不适用理由是否合理，性能目标是否有依据；不机械要求每个接口凑六组测试。

- 需求的问题、目标与范围是否清楚，产品行为是否有需求依据，有无未经确认的业务或外部契约变化。
- 事实是否各有唯一来源；稳定需求、场景、任务和设计引用能否追溯，有无互相矛盾的重复正文。
- Gherkin 是否描述可观察的行为，是否有真实测试绑定；缺失绑定或未运行结果是否被误报为已验证。
- 技术概要能否指导实施；公共/跨模块接口的签名、字段校验、输出、错误、副作用及关键步骤是否足以消除实质歧义，外部能力是否有依据。
- DSL 的任务、依赖、项目相对路径、验证命令和证据是否可执行且匹配本次功能；阅读计划是否由 DSL 生成。

不机械要求私有函数全部文档化、固定字数、两个方案、固定异常数量或固定步骤时长。只报告影响正确性、契约、可实施性或验证可信度的具体问题，不把个人格式偏好升级为缺陷。

输出实际审查方式与范围，问题列表包含严重性、文件位置或稳定 anchor、触发条件/冲突依据、影响和最小修正建议，并列出尚未验证的部分。结论区分已发现问题、无发现和证据不足；无发现直接说明无发现，不编造问题。有未解决的 critical/major 问题不得宣称通过。

独立性来自实际隔离的审查执行，不要求特定工具或模型；由原作者自查时必须标明自审，不能假称独立审查。
